## Area: core_store

I audited `crates/vec-core` and `crates/vec-store` read-only and changed nothing. Their 29 tests pass, but the bracket-filter test passes only by accident (finding 3). I checked findings 3 and 1 directly: the first with Python and sqlite3, the second by grepping every caller.

### 1. Bugs (most important first)

**1. Writing one file's index entries is not atomic, so a crash can lose that file's search entries for good.** High severity, high confidence.
- `Store` has no transaction API. `upsert_file` (`crates/vec-store/src/lib.rs:331`), `delete_chunks_for_file` (:365) and `insert_chunk` (:376) each commit on their own.
- The only caller (`crates/vec-index/src/lib.rs:678-720`) says "one DB transaction per file", but none exists.
- **Failure:** `upsert_file` writes the new hash first. If the process is killed or fails before the inserts finish, the file row carries the new hash with zero or partial chunks. The next `updatedb` sees the hash unchanged and skips the file, so it stays missing from search until `--full`.
- A reader running at the same time also sees the file with no chunks.
- **Fix:** a `Store::replace_file(path, mtime, hash, &[chunk])` that runs in one `conn.transaction()`.

**2. Model mismatch detection is never called, and a failed model load fills the index with fake vectors.** High severity, high confidence.
- `check_model` and `set_model` (lib.rs:208, :273, both `#[allow(dead_code)]`) are called only from tests. ARCHITECTURE.md ("Model mismatch detection: on startup…") describes a check that doesn't run.
- Meanwhile `load_embedder` (`crates/vec-core/src/lib.rs:15-64`) quietly returns `Embedder::stub(768)` on any failure: model missing, ONNX load error, Ollama unreachable, or `embed_url` empty.
- **Failure:** `vec updatedb` or `vec watch` run with a broken model path writes stub vectors with only a warning on stderr. Later real queries return nonsense.
- If you switch to an Ollama model with a different dimension, `dot` (lib.rs:810) zips to the shorter length and returns plausible-looking scores instead of an error. Its doc comment also wrongly says it "returns 0.0".
- **Fix:** have `load_embedder` return `Result` (stub only when asked for explicitly), call `set_model` on first index and `check_model` on every open, and reject a blob whose length is not `dim * 4` in `search`.

**3. `--path` filters break on paths containing `[`, `*` or `?`.** Medium severity, verified.
- The escaping order at lib.rs:435-441 is wrong: it replaces `*` with `[*]` and then turns every `[` (including the ones it just added) into `[[`.
- Checked with sqlite3:

| Filter | Pattern built | Matches |
|---|---|---|
| `/proj/[module]` | `/proj/[[module]*` | `/proj/[module]/…` **and** `/proj/module2/x` |
| `/a[b` | `/a[[b*` | nothing |
| `/a*b` | `/a[[*]b*` | `/a[b/x` and `/a*b/x` |

- Test `search_path_filter_with_bracket_char` (:1207) passes only because `normal` starts with `n`.
- **Fix:** map `[` to `[[]`, `*` to `[*]`, `?` to `[?]` in one pass. Better still, use the range scan already in `delete_files_where` (`path >= base/ AND path < base0`). It is faster, uses the index, and fixes the next item too.

**4. A `--path` filter matches any path that merely starts with the same characters.** Low severity, high confidence.
- `/proj/a` also matches `/proj/abc/…`, and `search_with_path_filter` doesn't test that case.

**5. Search pages through results with OFFSET and no snapshot, so results can be wrong and slow.** Medium severity, high confidence.
- lib.rs:449-522 runs the statement once per page with `LIMIT/OFFSET`, and each run sees a fresh WAL snapshot.
- If `vec watch` deletes or inserts chunks between pages, rows shift and some chunks are skipped or counted twice.
- OFFSET also re-reads all skipped rows each time, roughly O(N²/1000) work.
- **Fix:** keyset paging (`WHERE c.id > ?last`) inside one read transaction, or a single streaming `query` over all rows.

**6. `get_missing_file_paths` (lib.rs:556) uses `Path::exists`.** Low severity, high confidence.
- An unreadable or EACCES path is reported as deleted in `vec diff` (`crates/vec-index/src/lib.rs:1020`). The `is_gone` helper exists to avoid exactly this. Its doc comment (:553-555) is a stale copy of a different function's.

**7. Files with non-UTF-8 names are probably re-embedded on every run and never found.** Medium severity, medium confidence (I didn't trace the walker fully).
- Paths are stored with `to_string_lossy` (:312, :332, :620).
- A non-UTF-8 name is stored with replacement characters. Pruning then checks that mangled path (`is_stale` / `is_gone`) and probably deletes the row, so the file is re-embedded each run. At query time `can_read` fails on the mangled path, so it never shows up.
- **Fix:** store the raw `OsStr` bytes as a BLOB, or skip such files explicitly in the walker.

**8. Ranking misbehaves on NaN scores.** Low severity.
- A NaN or Inf in a stored embedding gives a NaN score. `score < min_score` is false for NaN, so it enters the heap, where `Ord` treats it as `Equal` (:131) and the heap ordering becomes inconsistent.
- **Fix:** skip non-finite scores.

**9. `util::can_read` doc says `access()` tests the effective UID** (`crates/vec-core/src/util.rs:4-6`). It actually tests the **real** UID/GID. That matters if anyone reasons about setuid or a daemon serving other users from this comment; `faccessat(AT_EACCESS)` checks the effective UID.

### 2. Improvements

- **Insert speed:** every chunk insert is its own commit, so one fsync each under WAL with default `synchronous=FULL`. Batching per file (fix 1) is an order-of-magnitude speedup. Also consider `PRAGMA synchronous=NORMAL` under WAL.
- **Search hot path:** each row allocates twice (`unpack_f32` and `normalize`). Store vectors already normalized at insert, then compute the dot product directly from the blob bytes with no allocation. Normalize the query once (already done).
- **Busy timeout:** none is set, so the store relies on rusqlite's implicit 5 s default. A long reindex from `vec watch` plus the daily timer can cause "database is locked" errors. Make it explicit and configurable.
- **Read-only opens:** query paths (search, MCP, status) open read-write and run `CREATE TABLE IF NOT EXISTS` and `create_dir_all`. Open with `SQLITE_OPEN_READ_ONLY` for queries, and use `PRAGMA user_version` for schema versioning or migrations.
- **Smaller cleanups:** `upsert_file` can use `RETURNING id` instead of a second SELECT, and `FileRecord` and `ChunkRecord` carry `#[allow(dead_code)]`.
- **Config typos are silently ignored:** none of the `Raw*` structs use `#[serde(deny_unknown_fields)]`, so `[serch]` or `bach_size` does nothing.
- **No value validation:** nothing checks `chunk_overlap < chunk_size`, `batch_size > 0`, `chunk_size > 0` or `max_file_size >= min_file_size`. An overlap of at least the chunk size risks a non-advancing chunk loop in vec-index (worth checking).
- **`exclude_dirs` and `exclude_files` can only append** (config.rs merge, around :354-358). A user can never re-include `build/`, `dist/` or `certs/`. Consider a `replace` form or `!pattern`.
- **Test gaps:** bracket filters (above), prefix-boundary filters, mismatched dimensions, crash atomicity, search during concurrent writes, and `resolve_model_path` (no tests at all). `load_none_succeeds` reads the real `/etc/vec.conf`, so it isn't hermetic. `byte_end_clamping_is_safe` tests local arithmetic, not product code.

### 3. Hardcoded values (under your rule)

- **Private LAN IP in source:** `crates/vec-core/src/config.rs:41` has the doc comment `"<private LAN address>"`. This exposes private network layout in git; replace it with a placeholder.
- **Stub dimension:** `Embedder::stub(768)` appears at `crates/vec-core/src/lib.rs:23`, `:34` and `:61`.
- **Search page size:** `SEARCH_PAGE_SIZE = 1_000` at lib.rs:88.
- **Busy timeout:** the implicit rusqlite 5 s default.
- **Compiled-in defaults** in `default_config()`: the model name `gte-multilingual-base`, `/usr/share/vec/models`, `/run/vec/embed.sock`, `/var/lib/vec/vec.db`, `/etc/vec.conf` (config.rs:268-373, :197), chunk and limit numbers, and the default `include_paths = ["/"]`. These are deliberate distro defaults, so this is a design conflict with your rule for you to decide on, not a clear-cut bug.
- **Error text:** the model-not-found message names the package `vec-model-gte` (config.rs:699), but the real package is `vec-model-base`.

### 4. Feature ideas

- `vec config check` / `vec config show`: print the merged config and which layer set each value, and fail on unknown keys.
- Store embeddings as int8 or f16, normalized. This covers the deferred "index compression" item in TODO.md and makes scans 2-4× faster.
- A `Store::replace_file` atomic API, plus a `meta.schema_version` key.
- Faster scoped search: when `--path` is given, push the path filter into an index range scan.
- `vec status`: show when the stub embedder or a model mismatch is in effect.

### 5. Doc drift

- **Config header comment** (config.rs:1-11) says "There is NO per-user config file". The code loads `~/.config/vec/config.toml`.
- **Model resolution order:** ARCHITECTURE.md says `{name}/model_int8.onnx`, then `model.onnx`, then `{name}.onnx`. The code (config.rs:677-694) tries `{name}.onnx` first, and the `resolve_model_path` doc lists only two forms.
- **Mismatch check:** ARCHITECTURE.md's "Model mismatch detection … on startup" is not implemented (finding 2).
- **`load_embedder` doc** presents the stub fallback as normal behaviour for the default backend; it isn't flagged as degraded anywhere.
- **`dot` doc** says it returns 0.0 on mismatched lengths; it returns a partial sum.
- **`util::can_read` doc** names the effective UID; `access()` uses the real UID (finding 9).
- **Storage comments:** the `crates/vec-store/src/lib.rs:1` header still says `src/store.rs`, and :553-555 is a duplicated doc comment.

Files reviewed: `crates/vec-core/src/{lib.rs,config.rs,util.rs}` and `crates/vec-store/src/lib.rs`. Callers I cross-checked: `crates/vec-index/src/lib.rs`, `crates/vec-cli/src/main.rs` and `crates/vec-mcp/src/lib.rs`.

## Area: index

I audited `crates/vec-index`, which is a single 1908-line file, `crates/vec-index/src/lib.rs`. I read it in full, then the store, config, embedder and watch code it calls. I confirmed the three chunker findings by compiling a copy of `chunk_file` in the scratchpad (`a scratch directory`). I changed nothing in the repo.

### 1. Bugs (most important first)

**B1. The chunker drops the end of a file when the last window snaps back (high, confirmed).** Lines 166–221. On the last window, the search for a function start (`fn`, `def`, …) can only look backwards, so it can end the chunk early at a function start. The loop then breaks because `start + step >= total_lines`. The lines after that point are in no chunk.
- Repro: a 20-line file whose `fn tail()` starts on line 17 gives one chunk, lines 1–16 of 20. The last function can't be found by search at all.
- Any small file, or any file whose final window has a function start in its last 5 lines, is affected.
- The same thing happens in the middle of a file when `chunk_overlap < BOUNDARY_SCAN` (5), for example `chunk_overlap = 0`: snapping back leaves lines between chunks.
- Fix: don't snap when `tentative_end == total_lines`, and start the next chunk from `snapped_end - overlap` rather than `start + step`.

**B2. `chunk_size = 0` crashes indexing (med, confirmed).** At line 196, `chunk_end_line - 1` wraps around, giving "index out of bounds … 18446744073709551615". Nothing in `vec-core/src/config.rs` validates `chunk_size > 0` or `chunk_overlap < chunk_size`. With `chunk_overlap >= chunk_size` the step becomes 1, so a file produces one chunk per line and embedding cost grows about 40×. Config loading should reject these values.

**B3. Writing one file's index entry is not atomic, so a crash can leave a file permanently half-indexed (high, confirmed).** `flush_pending` (lines 691–722) does `upsert_file` (new hash written first), then `delete_chunks_for_file`, then N `insert_chunk` calls. Each is a separate autocommit; there is no transaction anywhere in the store except the prune. If the process is killed, the disk fills, or an insert fails partway, the file row already holds the new hash with some or none of its chunks. The next incremental run sees a matching hash and skips the file, so it stays broken until `--full`. Fix: one transaction per file (or per batch), with the hash written last.

**B4. `--full` empties the index before re-embedding (med-high).** Lines 329–335 call `delete_all_files()` first. If embedding then fails (Ollama down, a model error), the run exits through `?` and the index is left nearly empty. A single chunk that fails to embed aborts the whole run (line 676), in incremental mode too. Better: build into a staging table or generation and swap at the end, and treat a failed embedding as a per-file error (`stats.errors += 1`, keep the old record).

**B5. `vec diff` disagrees with `vec updatedb` (med, confirmed).** `diff_files` (lines 965–1027) builds its own walker:
- It applies no `exclude_dirs` override, no `exclude_files`, no `max_file_size`/`min_file_size`, and no minimum-chunk rule. Excluded and too-small files show up as "new" forever.
- It reads every file whole with no size cap, which can mean multi-GB reads.
- "deleted" only lists files that no longer exist, so files that are now excluded never appear.
- Store errors are swallowed (`Err(_) => continue`, `unwrap_or_default()`).

It should reuse `scoped_walkers` plus the same filters as `index_walk`, pulled out into one shared "accept" function.

**B6. A relative `db_path` makes `IndexFilter` exclude every path (med, confirmed).** At line 909, `Path::new("vec.db").parent()` is `Some("")`, and `Path::starts_with("")` is true for every path. So `is_excluded` returns true and `vec watch` silently drops all events. Relative `include_paths` cause similar problems: they are only tilde-expanded (config.rs:430), so watch's absolute event paths never match them, and the walker stores relative paths. Config should require both to be absolute, or make them absolute.

**B7. `run_updatedb` with a path filter can silently do nothing (low-med).** Line 317 uses `std::path::absolute`, which on Unix neither resolves `..` nor follows symlinks. `vec updatedb --path ../x`, or a path reached through a symlinked include root, matches no include root: nothing is walked, nothing is pruned, and no warning is shown. Normalise the path, or warn when the filter falls outside every include path.

**B8. Symlink-swap race when indexing as root (low-med).** The walker checks the file type without following symlinks, but `metadata` and `read_to_string` (lines 764 and 808) do follow them. A user who swaps a file for a symlink to `/etc/shadow` between the walk and the read gets root-only content embedded into the world-readable (644) database. Embeddings can partly leak their content. The size check (line 787) and the read are also separate, so a file that grows in between is read without a cap. Fix: open with `O_NOFOLLOW`, `fstat` the open handle, and read through `take(max_file_size + 1)`.

**B9. `--full` with nested include paths embeds shared files twice (low).** Files under two include paths are re-embedded once per walk because `full` skips the hash check. Skip a path if it is already in `seen.kept`.

### 2. Improvements

- **Performance:** each `insert_chunk` is its own commit (one sync per chunk). Batching per flush in a transaction (B3) is also the biggest speedup available. `upsert_file` does an extra SELECT; `RETURNING id` would avoid it.
- **Snapping design:** only chunk ends snap; the next start is `start + step`, so a function header still lands mid-chunk. Start each chunk at a snapped boundary instead.
- **Small cleanups:**
  - `chunk_file` splits the content twice (lines 120 and 139); store the line `&str` in `LineInfo` instead.
  - `PendingChunk` clones the path and hash string for every chunk; use `Arc<Path>`/`Arc<str>` or a separate per-file table.
  - The `partition_point` grouping relies on a file's chunks being contiguous and never split across flushes. That holds today but nothing asserts it, and there is no check that `embeddings.len() == pending.len()`.
- **Rayon thread pool:** `build_global().ok()` runs on every walk. After the first call, a changed `index_threads` is silently ignored. Use a local `ThreadPool`.
- **Backend check:** `cfg.embed.backend != "ollama"` (line 627) is a string comparison. The daemon backend counts as "local", so batches are multiplied by core count for no benefit. Use an enum.
- **Weak tests:**
  - `chunk_overlap_between_consecutive_chunks` returns early when there are fewer than 2 chunks.
  - Both snapping tests accept anything within ±5 lines, which almost always passes.
  - No test checks that every line is covered (it would have caught B1).
  - Nothing tests B2–B6.
  - `test_cfg_for_dir` uses `Config::load(None).unwrap()`, which can read the real `/etc/vec.conf` and `~/.config/vec/config.toml`, so it isn't hermetic.
- **Exclude patterns:** an `exclude_dirs` absolute path outside the root (line 585) passes through unchanged and gets anchored to the root (`/opt/x` becomes `<root>/opt/x`). It should warn.

### 3. Hardcoded values (your config rule)

- `BOUNDARY_SCAN = 5` (line 36) is a chunking tunable; it belongs in `[index]`.
- `BOUNDARY_PATTERNS` (lines 43–58) is language policy and should be configurable. It also contains `"pub impl "`, which isn't valid Rust.
- `git_global(false)`, hidden files always skipped (also assumed in `IndexFilter`), `follow_links(false)`, and `git_exclude` tied to `gitignore` are all fixed policy with no config.
- The batch multiplier `batch_size * num_threads` is implicit.
- The `"ollama"` string literal (see section 2).
- Outside my scope but in the code path: `MAX_CONCURRENT = 4` in `vec-embed/src/lib.rs:412`, and the doc comment at `vec-core/src/config.rs:41` contains a private LAN address (`<private LAN address>`) and a model name, both now in git.

### 4. Feature ideas

- A per-file skip reason in `vec diff` and `--verbose` output (excluded / too large / binary / below minimum lines).
- A content hash stored per chunk, so an edited file only re-embeds the chunks that changed.
- Skipping the read for unchanged files using mtime plus size (the mtime is stored but never used for that).
- An `[index] max_chunk_bytes` limit, so very long lines (minified JS) don't produce oversized embeddings.
- Ending the run with a "files with errors" summary.

### 5. Doc drift

- The comment at lines 40–42 says the patterns cover C and C++; there are none.
- `ARCHITECTURE.md` (§Chunking) lists a different pattern set: it lacks `async fn`, `mod` and `pub impl`.
- The module doc's first line still calls the file `index.rs`.
- Line 92 says the step is "30 lines"; it actually comes from config.
- The `IndexFilter` doc says it "never excludes a path the walker would index", but its database-directory rule has no match in the walker. The two agree only if nothing indexable lives next to the database, and they disagree outright in B6.
- `ARCHITECTURE.md` says files that fail to decode are skipped, but `files_visited` still counts them.
- `TODO.md` "Watcher cleanup on delete" is still unchecked, though `update_paths` prunes deleted files and has a test for it (`scoped_update_prunes_deleted_file…`).

## Area: watch_daemon

I audited `crates/vec-watch` and `crates/vec-daemon` in full and edited nothing. The most serious problem is that `vec watch` can write meaningless placeholder vectors into the index, and nothing ever repairs them. Each issue below was checked against the code; I name it where I'm unsure.

### 1. Bugs

**B1. HIGH: the watcher can save placeholder vectors into the index, and they stay (high confidence).**
- **Where:** `crates/vec-watch/src/lib.rs:527`. `index_batch` calls `vec_core::load_embedder(cfg)` on every flush. That function (`crates/vec-core/src/lib.rs:15-63`) cannot fail: if the model can't be loaded, or Ollama is unreachable, it prints a warning and returns `Embedder::stub(768)`, a fake embedder whose vectors carry no meaning.
- **Scenario:** a model file is briefly unreadable during a package upgrade, Ollama restarts, or the network blips. The next flush embeds every changed file with the stub. The files' sha256 is stored as current, so later `vec updatedb` runs skip them as unchanged. Those files stay unfindable until someone runs `--full`.
- **Why the safety nets miss it:**
  - The retry-on-failure design (`lib.rs:133-145`) never runs, because no error is returned.
  - `Store::check_model` / `set_model` (`crates/vec-store/src/lib.rs:208,273`) are never called outside tests, so a wrong model or wrong vector size is never detected anywhere.
- **Fix:** load the embedder once at watch startup and return an error if it fails, or add a fallible `try_load_embedder` that returns an error instead of a stub. Also enforce `check_model` before writing.

**B2. HIGH (performance): the model is rebuilt on every flush (high confidence).** This is the same line as B1. A tract model compile takes seconds of CPU and 150-300 MB of memory churn per batch, every `debounce_ms`, on a service running at `Nice=19`. Keep the embedder alive for the life of `run_watch`; it is already built once per batch and passed by reference.

**B3. MEDIUM-HIGH: one idle client can freeze every user's queries (high confidence).**
- **Where:** `crates/vec-daemon/src/lib.rs:69-78,88-108`. The daemon serves one connection at a time and sets no read or write timeouts. The socket is `0666`.
- **Scenario:** any local user connects and sends nothing, or sends a length followed by fewer bytes. `read_exact` blocks forever, and every other user's `vec` query blocks too.
- **Client side:** `try_daemon_embed` (`crates/vec-cli/src/main.rs:883`) also has no timeouts, so queries hang forever instead of falling back to in-process loading.
- **Fix:** set read/write timeouts on both ends (taken from config), and serve each connection on its own thread or a small pool.

**B4. MEDIUM: the daemon can silently use a different model than the client (high confidence).** The protocol carries no model name, hash or vector size. If the daemon was started with an older model or a different `--config`, the client accepts any success reply (`main.rs:910`) and searches with mismatched vectors. Results are garbage and no error is shown. Fix: a handshake, or a reply header carrying model name, sha and dim that the client checks against config.

**B5. MEDIUM: indexing stalls while watches are being re-synced (high confidence).**
- **Where:** `vec-watch lib.rs:357` holds the `watches` mutex for a whole `reconcile`. That includes the complete `visit_dirs` walk, which on a root `.gitignore` edit or an overflow covers all include paths (the default include path is `/`).
- **Effect:** after each flush, the main loop locks `watches` only to read two counters (`lib.rs:129-132`), so indexing waits for the entire walk.
- **Fix:** walk outside the lock (compute the wanted set first, then lock to apply it), or keep the counters in atomics.

**B6. LOW: socket startup can delete the wrong thing (high confidence).** `vec-daemon lib.rs:43` removes whatever is at `socket_path` without checks.
- A second daemon instance takes over the first one's socket, and the first keeps running, orphaned.
- A misconfigured `daemon_socket` that points at a regular file deletes that file.
- **Fix:** check that the existing path is a socket and that connecting to it fails before removing it.

**B7. LOW: accept errors can spin the CPU (high confidence).** On a persistent `accept` error such as EMFILE, the loop at `lib.rs:76` spins as fast as it can and floods stderr. Add a backoff.

**B8. LOW: the daemon leaks internal details (medium confidence).** `lib.rs:118` sends `format!("{e:?}")`, the full debug error chain including internal paths, to any local user. Send `{e:#}` or a short generic message instead.

**B9. LOW: a narrow window to miss a new repo's ignore rules.** After `git init`, `.git` is not watched; only `.git/info` is. If `.git/info` is created after the re-sync walk triggered by the `.git` creation event, it never gets a watch, so later `.git/info/exclude` edits go unseen until the next re-sync.

**B10. LOW: the remove-old/add-new order on renames is not guaranteed (unconfirmed).** Re-syncing after a rename relies on notify sending the old-name event before the new-name event. If the new path is re-synced on its own first, re-adding a watch on the same inode returns the same descriptor. Removing the old path afterwards then drops the kernel watch that the new path depends on, while `Watches.dirs` still lists it. This should be confirmed against notify 6's inotify backend.

### 2. Improvements

- **Duplicate pending entries:** `Pending::insert` skips a path already covered by an ancestor, but adding an ancestor doesn't drop its descendants that are already pending, so they are walked twice. Prune them when inserting a directory.
- **Extra database open:** `write_status` opens the store a second time per flush. Reuse the store from `index_batch`.
- **Daemon hardening:** the system `contrib/vec-embed.service` runs as root, with no `User=`, parsing an ONNX model and serving a world-writable socket. Add `DynamicUser=yes`, `ProtectSystem=strict`, `NoNewPrivileges=yes`, `PrivateNetwork=yes`.
- **Daemon output:** builds the reply with `flat_map` into a `Vec` with no preallocation, and makes three separate `write_all` calls. Preallocate with `with_capacity(8 + n*4)` and send it in one write.
- **Daemon tests missing:**
  - `run_daemon` itself: stale-socket removal, permissions, a second instance.
  - A client that stalls mid-request.
  - A body shorter than the stated length.
  - Invalid UTF-8 (currently replaced silently by `from_utf8_lossy`; it should be rejected).
- **Watch tests missing:**
  - Nothing tests the flush path with a failing embedder; this is exactly the B1 gap.
  - Nothing tests `run_watch` or the watch manager end to end in this crate.
  - The unit tests use `Instant::now()`, which conflicts with TESTING.md's "no `std::time`" rule.
- **Dependency:** `notify = "6"`; notify 8 is current.

### 3. Hardcoded values (your config rule)

- `vec-daemon/src/lib.rs:94`: the 1 MiB request limit (`1_048_576`).
- `vec-daemon/src/lib.rs:59`: socket mode `0o666`.
- No I/O timeouts exist in the daemon or the client. Once added, they must come from config.
- `vec-core/src/config.rs:154`: a built-in default `daemon_socket = "/run/vec/embed.sock"`.
- `vec-cli/src/main.rs:509`: `~/.local/share/vec/embed.sock` hardcoded in the setup output.
- `vec-core/src/lib.rs:23,34,61`: stub dimension `768`, which the watcher reaches through B1.
- vec-watch itself is clean: all tunables are in `[watch]`.

### 4. Feature ideas

- **Reload config without restart:** handle SIGHUP or watch the config file in `vec watch`. This would remove the "needs a restart" limitation in BUGS.md.
- **Socket-activated daemon:** a systemd `.socket` unit plus an exit-after-idle timeout (configurable). The model loads only on first query and memory is freed when idle, which removes the main "150-300 MB permanent RAM" argument against enabling it.
- **Batch request in the daemon protocol,** so `vec watch` (and `updatedb`) can share the daemon's already-loaded model instead of loading their own.
- **systemd readiness and watchdog** (`sd_notify` READY/WATCHDOG) for both services.
- **More watcher status:** pending count, overflow and rescan counts, and the last successful flush time in `meta`, shown by `vec status`.

### 5. Doc drift

## Area: embed_cli_mcp

I audited vec-embed, vec-cli and vec-mcp read-only: nothing was edited or committed. The most serious finding is that the index can silently fill with random vectors when the model fails to load. I reproduced one panic with the existing binary (`vec context README.md:9999` crashes at `main.rs:665`, exit 101); everything else below comes from reading the code.

### 1. Bugs (most important first)

1. **HIGH, index filled with random vectors that never get fixed.** `vec-cli/src/main.rs:367` (`cmd_updatedb`) calls `vec_core::load_embedder`. When the model is missing or broken, or Ollama can't be reached, that function only prints a warning and returns `Embedder::stub(768)`. `run_updatedb` then indexes random vectors under real file hashes, so later incremental runs see the files as unchanged and never replace them. Nothing would catch this either: `Store::check_model` (vec-store:208) and `Embedder::model_sha256` (vec-embed:286) are both `#[allow(dead_code)]` and nobody calls them. `Embedder::model_name()` returns `"tract-onnx"` for every ONNX model, so swapping models isn't detectable by name. Confidence: high. Fix: make `updatedb`, `watch` and `daemon` refuse to run with the stub, and call `check_model` with name, sha and dimension.

2. **HIGH, dimension mismatch gives garbage scores with no error.** `vec_store::dot` zips the two slices, which silently truncates to the shorter one. A query embedded by a different model or backend (stub, Ollama, or a stale daemon still running the old model) scores against every chunk without complaint. The CLI's `try_daemon_embed` (main.rs:883) never checks the returned length against the index's stored dimension. Confidence: high.

3. **MED, panic in `vec context`, confirmed.** main.rs:665. When the requested line is past the end of the file, `from > to` and the slice panics: `range start index 9988 out of range for slice of length 315`.

4. **MED, the same panic in search snippets, CLI and MCP.** main.rs:340 and mcp/lib.rs:167. If a file shrank after indexing, `best_line_in_content` returns `None`, the code falls back to the stale `start_line`, and that slice panics too. In MCP the panic happens inside a tool handler. Confidence: high.

5. **MED, panic on a non-character boundary.** main.rs:973 and mcp/lib.rs:352 take `&content[start..end]` using byte offsets stored in the DB. If a file with non-ASCII text was edited since indexing, an offset can fall in the middle of a UTF-8 character and the slice panics. Use `content.get(start..end)` instead. Confidence: high.

6. **MED, `vec serve` ignores `--config`.** main.rs:173 calls `vec_mcp::run_server()`, and `VecServer::new()` (mcp:279) calls `Config::load(None)`, so `vec --config X serve` uses the default config chain.

7. **MED, the MCP server loads the whole ONNX model on every `search` call.** mcp:127. Each tool call pays the full graph compilation. It also ignores `backend = "ollama"` and the daemon socket, and quietly falls back to `stub(768)` (mcp:341). An Ollama setup therefore gets random results through MCP. Load the embedder once (lazily, kept on the server) or go through `embed_query`.

8. **MED, the MCP `context` tool reads any file and has no size limit.** mcp:201–219. `can_read` is `access()` for the server's own user, so it only filters what the user could read anyway. A prompt-injected agent can read `~/.ssh/id_*`. `file_path = "/dev/zero"` makes `read_to_string` run until memory is exhausted. Restrict it to indexed files (or include_paths), require a regular file, and cap the size. The CLI `context` (main.rs:660) has the same lack of a size cap.

9. **MED, `similar` and `explain` don't work with relative paths as the README shows.** main.rs:686–689 and 788–789 pass the user's string straight into DB lookups, but the DB stores absolute paths. `vec similar src/auth.rs:42` (README:184) always reports "no chunk covers". The self-match check at line 699 compares strings and has the same problem. `--path` and `--exclude` (lines 158, 264) aren't canonicalized either, so a relative `--path .` matches nothing. Fix: `std::path::absolute` or `canonicalize`.

10. **MED, multi-query search loads the model once per query.** main.rs:220. `embed_query` calls `load_embedder` for each query string when the daemon isn't running, so `vec "a" "b" "c"` compiles the model three times.

11. **LOW–MED, the HTTP client in vec-embed is fragile.**
    - `&json_body[..200]` (vec-embed:569) panics on a non-character boundary, for example a non-ASCII error body from Ollama.
    - `decode_chunked` runs after `from_utf8_lossy`. Chunk sizes count raw bytes, but replacement characters change byte lengths, and `remaining[..chunk_end]` (622) can panic in the middle of a character. Decode chunks on the `Vec<u8>` first.
    - The HTTP status is never checked, so errors show up as a confusing "missing 'embeddings'".
    - Values that aren't numbers become `0.0` without warning (583).
    - `TcpStream::connect` has no connect timeout, and the `set_read_timeout(...).ok()` result is ignored.
    - Any path part of `embed_url` is dropped silently (482).
    - Only `http://` is supported.

12. **LOW, CLI search returns fewer than `limit` results.** main.rs:260–268 truncates to `limit` before the `--exclude` and `can_read` filters. `cmd_similar` and `cmd_repl` have the same behaviour.

13. **LOW, `try_daemon_embed` can hang.** main.rs:883 sets no read or write timeout, so a stuck daemon hangs the CLI forever. It also trusts `data_len` (up to 4 GiB) and allocates that much.

14. **LOW, wrong assumptions about model input order.** vec-embed:176 sets `has_token_type_ids = input_count >= 3`, and `run_tract` feeds inputs by position as (ids, mask, types). An export that orders them (ids, token_type_ids, mask) gets the wrong tensors without any error. Map inputs by name instead. Padding uses token 0 (XLM-R's pad token is 1); that's harmless only because the mask covers it.

15. **LOW, `vec status` mislabels a value.** It shows `MAX(mtime)` of indexed files as "Last indexed" (main.rs:410). That is the newest file modification time, not the time of the last run.

16. **LOW, panic or bad output in `init` and `model download`.** `cmd_model_download` indexes `model_search_path[0]` (main.rs:459) and panics if the configured list is empty. `init --user` falls back to a literal `"~"` home and puts paths into TOML strings without escaping, so a `"` or `\` in a path breaks the file.

### 2. Improvements

- **Inference is slow by design.** vec-embed always pads every chunk to `max_tokens` and runs batch=1. The comment at vec-embed:178 claims a "symbolic batch dimension", but the shape is `tvec!(1, max_tokens)`. A symbolic sequence dimension or length buckets (32/64/128) plus real batching would cut indexing time a lot. The HTTP backend also sends one text per request even though `/api/embed` accepts arrays.
- **Duplicated code.** `best_line_in_content` and the snippet rendering are copied between the CLI and MCP; they belong in one shared helper, fixed once (items 4 and 5). MCP search also skips `path_boost`, so the CLI and MCP rank results differently.
- **Blocking work on the async runtime.** The MCP tools run SQLite queries, file reads and model loading directly on tokio worker threads; use `spawn_blocking`.
- **`vec repl`.** One embedding error ends the whole session (`?` at 735), and it ignores `min_score`, snippets and `path_boost`.
- **Path boost.** Short words like "a" or "in" match nearly every path, and the boosted score can go above 1.0.
- **Test gaps.**
  - Snippet and context bounds (shrunk file, line past the end).
  - Offsets on non-ASCII text.
  - `parse_file_line` with Windows-style or colon-containing paths.
  - `decode_chunked` and HTTP response parsing.
  - `try_daemon_embed` against a mock socket.
  - MCP handler tests.
  - vec-embed has no test with a real or tiny ONNX model.
- **Positional query vs subcommands.** A bare query can't be a subcommand name, so `vec diff` can't be used to search for "diff". Add a `vec search` subcommand or a `--` escape.
